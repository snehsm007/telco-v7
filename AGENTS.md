# AGENTS.md: building a GECX / CX Agent Studio agent from a PRD

This repository builds a conversational agent on **Google Customer Experience Agent Studio** (**CXAS**; the platform is also called **Customer Engagement Suite** (**CES**) or **Gemini Enterprise for Customer Experience** (**GECX**)). The agent serves both text (web chat, Short Message Service (**SMS**)) and voice (phone calls). Coding agents (Antigravity, Jetski, Claude Code, Gemini Command-Line Interface (**CLI**), …) work here under the rules below.

Where the detail lives:
- **What goes where** (agents, prompts, tools, state, callbacks): [docs/DESIGN_RULES.md](docs/DESIGN_RULES.md), 36 rules learned across our practice build, a reference build that reported 100%, `telco-rebuild` (`60/70` strict `3/3` at `0bf79fe`), and `telco-v3` (`66/70 = 94.3%` combined strict `3/3` at `8bdb778`; `70/70 = 100.0%` combined majority, `18/20 = 90.0%` holdout strict `3/3`, and `58/60 = 96.7%` holdout trials at `f05719b`). Rule numbers below that say "DESIGN_RULES rule n" point there.
- **How to lay out a prompt:** [docs/INSTRUCTION_STYLE.md](docs/INSTRUCTION_STYLE.md).
- **The reasons, in plain English:** [docs/BEST_PRACTICES.md](docs/BEST_PRACTICES.md).
- **The step-by-step procedure:** the **`gecx-agent-playbook`** skill (`.agents/skills/gecx-agent-playbook/SKILL.md`, with phase references `references/01-*.md` through `14-*.md`).
- **Platform tools:** the built-in **SCRAPI** (Scripting and Command-line Interface for Rapid Agent Prototyping and Integration: Google's software development kit (**SDK**) and CLI for CXAS) skills (`cxas-agent-foundry`, `cxas-composite-voice-agent-optimizer`, `cxas-loss-analysis`, `cxas-sim-eval`, `cxas-configurable-dashboards`, `cxas-autolabel-rules`). They appear under `.agents/skills/cxas-*` only after the optional `uv run cxas init`; this kit ships only `.agents/skills/gecx-agent-playbook/`. **Always read the SCRAPI skills and playbook references before exploring Python packages or writing any custom script.** Don't use the global `gecx-3hr-sprint` skill: its time target was never measured and it conflicts with these rules (Rule 33).

The human owner may be new to this stack. **Explain in plain, beginner-friendly English**, define every acronym the first time you use it, and keep status updates concise.

## Starting a new agent from this kit

Each new agent gets its own copy of this starter kit. Clone it into a new folder, then remove the starter kit's git history so the new agent starts with a clean repository:

```bash
git clone git@github.com:snehsm007/gecx-agent-starter.git my-agent
cd my-agent && rm -rf .git && git init   # gives the new agent its own fresh history
```

Replace `my-agent` with the agent's name, place the **Product Requirements Document** (**PRD**) in `prd.md`, and choose either the **Fast-Track Kickstart** (recommended) or the multi-gate **Structured Phases** below.

## Inputs
- `prd.md`: the Product Requirements Document (PRD). It is the single source of truth for scope. If something is missing or ambiguous in the PRD, surface it in the single-turn kickstart table below; never silently invent business rules.
- Optional: public or benchmark evaluations, sample conversations, Application Programming Interface (**API**) specifications, brand guidelines, or an existing agent export.

## Fast-Track Kickstart (recommended first-day path)

**Why:** drafting dozens of decisions before running a single cloud conversation delays finding out how the platform really behaves: how strict the Large Language Model (**LLM**) judge is, simulated callers who were given no account facts, whole-number session variables reaching tools as decimals. The kickstart folds Phases 1–5 into one short loop while keeping full test coverage and human sign-off. Detailed recipe: [references/14-fast-kickstart-and-eval-patterns.md](.agents/skills/gecx-agent-playbook/references/14-fast-kickstart-and-eval-patterns.md).

1. **Audit the evaluations first** (`python3 scripts/inspect_evals.py --evals-dir <path>`), before writing tools or prompts. Check:
   - **(a) Languages (the telco sample uses `en-US`, `fr-CA`, `es-US`; take yours from the PRD and the tests):** every line the agent speaks in a journey must be written in that journey's language in the prompt; ordinary tools return data, not sentences, while `handover_to_person` returns localized `spoken_message` / `handoff_message` from `SPOKEN_LINES` for `speech_hygiene` fallback (DESIGN_RULES rules 5 and 25).
   - **(b) Fact-less simulated callers:** which tests give the caller no phone number, One-Time Passcode (**OTP**), Personal Identification Number (**PIN**) or card digits (`scenario.userFacts`, `variableOverrides`)? Keep the fake world lenient via the 3-attempt login ladder (DESIGN_RULES rule 21), and have the agent send a login code and ask for it back rather than asking the caller to confirm numbers they were never given.
   - **(c) Exact wording:** which expectations check an exact sentence? If the PRD requires the sentence, write it word for word in the prompt step that speaks it, with its failure line next to it; if only a test requires it, leave it out. Reference numbers and amounts come from tools (DESIGN_RULES rules 5, 6 and 8).
   - **(d) PRD-vs-test friction:** where a strict PRD rule collides with a test, for example a PRD limit that a test expects the agent to exceed, or a lenient fake login vs. a "wrong code three times" lockout test (solved by the 3-attempt login ladder and `scripts/eval_contract.py` — see `docs/DESIGN_RULES.md` Rules 21–23).
2. **Put every open PRD question in ONE approval table.** Read `prd.md` and draft `docs/requirements.md`, `docs/scenarios.md` and `docs/tdd.md` (**Technical Design Document**, **TDD**) in one pass, following DESIGN_RULES.md unless the PRD says otherwise. The defaults, in short:
   - **Model & voice:** Gemini Composite V1 (`gemini-composite-v1`), `temperature: 1.0` (`TEMPERATURE ?= 1.0`; final, because `0.2` made no measurable difference; DESIGN_RULES rule 17), and `noiseSuppressionLevel: "HIGH"` on channel profiles and phone deployments. Write per-language Director's Notes yourself: the scaffold doesn't generate them yet, and its `cxas_app/cxaslint.yaml` turns off lint rules A007/A009 meanwhile.
   - **Agents:** a first agent that only greets, finds the account and routes, plus one specialist per PRD module (one agent only if the PRD has a single job; Hard Rule 2). Each specialist logs the caller in itself when its task needs it.
   - **Prompts and tools:** every spoken line lives in the prompt, in every language; ordinary tools return data in one shape (`status`, `data`, `error_message`, `tracking_id`), never sentences (`handover_to_person` is the single exception returning localized `spoken_message`/`handoff_message`; DESIGN_RULES rules 5 and 25), and localize descriptive status/delay notes by `resolve_locale` (DESIGN_RULES rule 33). Money goes out as a number plus a 2-decimal display string (`amount: 85.5, amount_display: "85.50", currency: "CAD"`, built with `display_amount()` in `lib/replies.py`; DESIGN_RULES rule 27). Use union types (`str | int | float`) on tool parameters for numeric/float coercion and never put `from __future__ import annotations` in tool wrappers (DESIGN_RULES rule 32). Pre-ground Turn N+1 follow-up FAQ fields in action/catalog tools (DESIGN_RULES rule 33), wrap predictable multi-turn tool chains into atomic single-turn calls and support empty/placeholder inputs for info-first caller openers (DESIGN_RULES rule 34), and never return open-ended `"up to full monthly rate"` tool wording that baits the simulated caller into demanding over-cap credits (DESIGN_RULES rule 35).
   - **State:** flat, typed variables, one fact each (`language` defaults to `""`, never `"en-US"`; DESIGN_RULES rules 15 and 25).
   - **Callbacks, safety and privacy:** keep only the `speech_hygiene` (`after_model_callback`) callback; never add `before_tool` `auth_gate` or `before_model` `turn_state` callbacks (DESIGN_RULES rule 16); safety guardrails on from the first push; run `make setup-dlp ENV=staging` once so Cloud Data Loss Prevention (**DLP**) masks personal data in logs, then `make push` (DESIGN_RULES rule 26).
   - **Fake world (`lib/fakes.py`):** accepts 9–10 digit caller-stated numeric phone/account identifiers (guarded with `not any(c.isalpha() for c in raw)` before synthesizing phone numbers; DESIGN_RULES rule 22) and uses the 3-attempt login ladder (DESIGN_RULES rule 21), verified offline by `scripts/eval_contract.py` (`make eval-contract`; DESIGN_RULES rule 23).

   Present the genuine ambiguities as one compact markdown table with your recommended default for each, and get one "Approved" reply from the human.
3. **Scaffold the agent and pass offline CI.** Run `make kickstart NAME=<agent-name> PRD=prd.md` (it calls `scripts/kickstart.py --agent-name <agent-name> --prd prd.md`). It writes a `router` agent (greets, finds the account, routes), a `specialist` agent (logs the caller in itself when a task needs it, then does the task), six small tools that share one reply shape and read session state (`lookup_account(phone_or_account)`, `send_login_code`, `check_login_code`, `check_secret_pin`, `submit_request`, `handover_to_person`; the platform's built-in `end_session` comes on top), one speech-cleanup callback, `lib/{fakes,replies,services,speech}.py`, one test file per code file in `tests/`, and starter evals in `evals/`. `make bundle` and `make ci` pass before you change anything (`make ci` fails on any `cxas lint` warning not listed in `lint_waivers.json`, and when `cxas` is not installed). Rename `specialist` and `submit_request` after the PRD's modules and tasks, and replace the placeholder spoken lines with the PRD's wording.
4. **Push to a new staging app and run a 3-case cloud smoke test:** commit, then `make push ENV=staging`, `make push-evals ENV=staging`, and `make bench-smoke ENV=staging TARGETS=<3_core_evals>`. `make preflight` runs automatically before each cloud target. Read the real cloud transcripts and all three judge metrics before building out the remaining tools and journeys.

Then hill-climb under Rules 21–33, and run the hidden holdout once, at the end, on the same code as a full visible run that passed Gate 3 (Rule 30). For neighbouring jobs use the SCRAPI skills: `cxas-dfcx-migration` to move a Dialogflow CX (**DFCX**) agent to GECX, `cxas-composite-voice-agent-optimizer` (`make voice-audit`) for voice naturalness, and `cxas-loss-analysis` to cluster failed transcripts.

## Structured Phases and Approval Gates
| # | Phase | Output | Human approval? |
|---|---|---|---|
| 1 | Requirements | `docs/requirements.md`: every PRD requirement numbered `REQ-n`, with priority P0 (must-have) / P1 (should-have) / P2 (nice-to-have), plus batched open questions and defaults | **Yes** (combine 1–3 into one table in Fast-Track mode) |
| 2 | Scenarios | `docs/scenarios.md`: every `REQ-n` expanded across Critical User Journey (**CUJ**) scenario buckets | **Yes** (combined in Fast-Track mode) |
| 3 | Design (TDD) | `docs/tdd.md`: agents, tools (exact inputs/outputs), flat typed session variables, routing, callbacks, voice rules, coverage map | **Yes** (combined in Fast-Track mode) |
| 4 | Tests first | `evals/*`, `tests/*`: unit, contract, callback, and evaluation suites | No |
| 5 | Build | `cxas_app/` + `lib/`: scaffold via `make kickstart`, bundle via `make bundle`, verify via `make ci` | No |
| 6 | Text evals on staging | Push to `-staging`, run baseline evaluations, classify `evals/unstable_set.txt`, label failures `real` / `judge` / `infra` | No |
| 7 | Hill-climb fix loop | Root-cause cluster diagnosis → Gate 0 offline proof (`make ci` + `make impact`) → commit + `make push` → Gate 1 `make smoke-impact` → Gate 2 `bench-unstable` → Gate 3 `bench-full` + `make gate3` (`strict 3/3 >= 90%` AND `100%` majority) | Only for architecture changes, relaxed tests, or holdout-driven fixes |
| 8 | Audio evals | Run after text passes: speech naturalness + task outcome on audio simulations + noise variant | No |
| 9 | Deploy | Continuous Integration (**CI**) gate → live version → post-deploy smoke test | **Yes** (first deploy) |

Stop and ask the human whenever:
- an approval gate marked **Yes** finishes;
- a fix changes the architecture (adding or removing agents, changing PRD tool contracts);
- a test or evaluation rubric would be made easier to pass;
- a fix is driven by a holdout result (it needs the owner's approval, then a full visible run on that same code (same source fingerprint); Rule 30);
- a file, repository, API, or Google Cloud Platform (**GCP**) resource cannot be read or reached.

## Hard Rules (1–13)
1. **Tests before code.** Every P0 (launch-blocking) requirement has at least one automated test and evaluation that CI runs on every change (a "gated" test).
2. **Router plus specialists by default.** Start from the scaffold's layout: a router that greets, finds the account and routes, plus one specialist per PRD module. Use a single agent only when the PRD has a single job. Add, split or merge agents beyond that only when measurements prove that instructions, tools, or callbacks cannot fix a routing or context failure, and document why in `docs/tdd.md`.
3. **Facts come from tools, never from the prompt.** Never put realistic example data (prices, dates, ticket numbers, phone numbers) or test material in `instruction.txt`: the LLM copies it into live replies. Every spoken fact, including `$0.00` fee waivers, tax notes, timelines and policy terms, is returned as a field in a tool result, and prompts forbid inventing or extrapolating any unreturned security/fee/timeline explanations (DESIGN_RULES rules 7, 8 and 10).
4. **The same tool contract everywhere.** Instruction text, Python tool code, fake services (`lib/fakes.py`), unit tests, and `docs/tdd.md` must use identical tool names, parameter names, and allowed enum values. A contract test in `tests/` enforces this automatically. Extend it so it also checks that every field, allowed value (enum) and timeline the PRD requires comes back from the tool with the PRD's exact value (for example `"bank_account"`, never `"bank"`). Money is returned as a number plus a 2-decimal display string (DESIGN_RULES rule 27).
5. **Only behavior evaluations count.** A score from keyword matching, YAML (YAML Ain't Markup Language) syntax checks, or offline string checks that never ran the live model on the platform is **not** an evaluation score. Never report it as one.
6. **Code checks override the LLM judge.** Every transcript is checked by `suite/grader.py` (leaked Python code, facts stated before a tool call, dead air, wrong language, leaked internal agent/tool names, markdown/emoji in voice replies). A deterministic code-check `FAIL` always overrides an LLM judge `PASS`.
7. **The judge is at least as strong as the agent model**, and is verified against hand-labelled transcripts in `evals/calibration/` whenever the judge model or expectations change.
8. **Label every failure**: `real` (the agent did the wrong thing), `judge` (the agent was right; the grader or rubric expectation is wrong), or `infra` (quota HTTP 429/503/504, credential expiry, platform outage). Only `real` failures change the agent.
9. **Never move the goalposts.** Editing a test or evaluation expectation so it passes requires a PRD-backed reason in the commit message and explicit human approval. Never truncate multi-turn goldens to 1-turn checks.
10. **Text first, audio last.** Voice evaluations consume separate, smaller concurrency quotas and take longer. Run audio evaluations only after the text evaluation gate is green.
11. **Log every run** to `history/runs.jsonl` (JSON Lines format: git Secure Hash Algorithm (**SHA**) commit hash, app version, agent model, judge model, per-test result, and change note) and benchmark summaries to `history/bench/*.json`. **Never** write synthetic composite `full-*` records combining slices from different runs or git SHAs into `history/runs.jsonl`.
12. **Never touch live by hand.** Production (`live`) changes happen only through CI after the staging gate passes. Use the `-staging` app or per-Pull-Request (**PR**) preview apps for all experiments.
13. **Access problems: stop and say so.** Never guess the contents of a file, repository, URL, or cloud resource you could not read.

## Engineering Rules (14–20)
14. **Makefile first.** Run all tasks through `make <target>`, never ad-hoc shell commands. CI invokes the exact same targets. If a workflow lacks a target, add one to `Makefile`.
15. **The model understands, Python decides.** The model turns caller speech into tool arguments (`intent="bill_dispute"`); Python does the calculations, eligibility rules and state changes. In practice (DESIGN_RULES rules 9–11, 21–24):
    - **Check inputs before acting:** a tool validates its arguments (digit counts, allowed values) after normalizing codes with `normalize_code(value)` (strips trailing `.0` float strings before extracting digits; DESIGN_RULES rule 22) and returns an error code with an `agent_action` hint instead of acting.
    - **Confirm only after success:** a state-changing tool returns `status: "ok"` plus the facts to confirm (reference number, amount), never a sentence. The prompt holds the success line with the failure line right next to it.
    - **One tool per fixed sequence:** tools called in the same turn all run before any result comes back, so chain fixed steps (take a payment, update the account, send a receipt) inside one tool, and have a money-moving tool check `logged_in` in `context.state` itself (while login tools auto-populate the default profile when `account_id` is empty and never gate on `NOT_IDENTIFIED` or `CODE_NOT_SENT`; DESIGN_RULES rule 21).
    - **Tools read and write session state:** a tool sees the session's variables as `context.state` (a plain dictionary), and what it writes is visible to later tool calls and turns (confirmed live on 2026-10-08). The tool's own Python memory (globals, caches) does not survive a call. Declare every key a tool touches in `app.json` (`cxas lint` rule V100), and convert whole numbers with `read_count(state, key)` (`int(float(v))`), because they arrive as decimals (`5.0`).
16. **Fake data lives in one place (`lib/fakes.py`) and is verified by `scripts/eval_contract.py`.** Only `lib/fakes.py` holds fake records, behind service functions in `lib/services.py`; other code refers to them by name (`make overfit-check` enforces `NUMBER_IN_PROMPT` and `EVAL_VALUE_IN_FAKES`, and `make eval-contract` runs `scripts/eval_contract.py` to verify `lib/fakes.py` against `bench/dev/evaluations/`). Login tools follow the 3-attempt ladder (DESIGN_RULES rules 21–23).
17. **Shared code lives in `lib/` and is bundled.** Each tool and callback runs in the cloud as one standalone file, so `from lib.x import y` works in `pytest` but fails on the platform unless bundled. Write shared code in `lib/` and run `make bundle` (`suite/bundle.py`). Never edit the generated block (from `# --- BEGIN GENERATED SHARED BUNDLE` down) by hand, avoid duplicate helper names across `lib/*.py`, and keep each tool wrapper's parameters identical to its `<tool>_impl` in `lib/services.py` (the injected `state` parameter aside); `make bundle-check` fails on a mismatch.
18. **Revert first.** If a fix starts spreading across many files or breaks passing tests, stop, `git revert` or reset it, and find the smallest deterministic fix. After a target evaluation passes, strip any leftover rules from earlier attempts and re-verify.
19. **Every Python file has ≥80% test coverage and its own test file** (`cxas_app/tools/<name>/.../python_code.py` → `tests/.../test_<name>.py`, `lib/<mod>.py` → `tests/test_<mod>.py`). `make ci` and `suite/coverage_check.py` enforce both.
20. **One instruction layout: silent sub-agent transfers; one-turn spoken human handovers.** Every `instruction.txt` uses `<role>`, `<persona>`, `<response_protocol>`, `<constraints>`, and `<taskflow>`. Inside `<taskflow>`, every step is `<subtask name="…">` → `<step name="…">` with exactly one `<trigger>` (when) and one `<action>` (what). Refer to tools and agents as `{@TOOL: name}` and `{@AGENT: name}`. For normal tool calls, emit the tool call first and wait for its result before speaking; sub-agent transfers emit only the tool call. **EXCEPTION — Handover to a person (`handover_to_person`):** in a **single turn**, speak the required transfer line (using the step-specific transfer line if the workflow step defines one, otherwise the generic closing line), call `handover_to_person`, and call `end_session` together, backed by `speech_hygiene` (`after_model_callback`), which adds `state["handoff_message"]` only when the reply has no text and never replaces text the model spoke (DESIGN_RULES rules 5, 7, 20, 25). Full specification: `docs/INSTRUCTION_STYLE.md`.

## Hill-Climb & Evaluation Rules (21–33)
Why these exist: multi-turn LLM simulations vary from run to run on borderline cases. At a `p = 92.0%` individual pass rate, `50 * p^3 = 38.9/50` strict `3/3`, while majority vote (`>=2/3`) hides 8–10 coin-flip evaluations. A test that fails 1 time in 5 passes strict `3/3` only about 51% of the time (`0.8^3`), so one failed repeat is a signal, not noise. Without an impact-smoke gate and strict-first tracking, teams chase noise or introduce regressions: `telco-rebuild` lost about 7 hours (6.96 h) to 5 preventable regressions and their reverts. Details for rules 22–24 and 27: [references/07-failure-loop.md](.agents/skills/gecx-agent-playbook/references/07-failure-loop.md).

21. **Real platform evaluations are the score, stated strict `3/3` first.** Progress is reported only as platform evaluation results with cloud evaluation run IDs, always as `strict 3/3 | majority >=2/3 | individual`, in that order (plus individual pass rate `p` and `N * p^3`). After editing `lib/`, `cxas_app/` or `evals/`: commit, run `make impact` (`scripts/impact.py`) to list the evaluations the change can affect, `make push ENV=staging`, then `make smoke-impact ENV=staging` (3 repeats). Keep the commit only if impacted evaluations pass `3/3` with `0` tool errors and nothing else regresses.
22. **Confidence Ladder & Dual-Metric Gate 3 Bar (`strict 3/3 >= 90%` AND `100%` majority).** Every candidate fix climbs these gates in order and stops at the first gate it fails. The `Makefile` enforces the order push → smoke → full run: `make push`, `make smoke-impact`, `make bench-full` and `make bench-holdout` refuse while `cxas_app/`, `lib/` or `evals/` have uncommitted changes ("commit, then make push"); `make smoke-impact` refuses unless the deployed code matches the current code (same source fingerprint); from the second full run on, `make bench-full` refuses unless that smoke passed.
    - **Gate 0, offline (free):** `make ci` green (`bundle-check`, `overfit-check` including `NUMBER_IN_PROMPT` and `EVAL_VALUE_IN_FAKES`, `eval-contract` when `bench/dev/evaluations` exists, `cxas lint` with 0 errors and 0 warnings not listed in `lint_waivers.json`, `pytest` + ≥80% per-file coverage, suite self-tests, `verify_mutations.py`; it fails if `cxas` is not installed), `make voice-audit`, and a unit test replaying the failing conversation's recorded tool inputs and outputs. The diagnosis must account for **all three** judge metrics (Custom Expectations, User Goal Satisfaction, Hallucination/Grounding).
    - **Gate 1, impact cloud smoke (median about 6 minutes across 33 `telco-rebuild` smoke runs):** commit, `make impact`, `make push ENV=staging` (it records the commit's source fingerprint in `history/last_push.json`), then `make smoke-impact ENV=staging`. It runs the impacted evaluations × 3 and records the verdict for that fingerprint (0 impacted evaluations counts as a pass). `make impact` prints a `Verdict:` line; the verdict is `FULL` when `global_instruction.txt`, `app.json`, `lib/speech.py`, `lib/replies.py`, a shared helper in `lib/services.py`, or the shared login/fake-account code changed, or when the impacted set covers every evaluation. On a `FULL` verdict, `make smoke-impact` exits with code 2 and tells you to run `make bench-full`. Advance only if impacted evaluations pass **`3/3` strict** with **zero** tool errors. For a manual smoke, `make bench-smoke ENV=staging TARGETS=<id1,id2>` runs named evaluations × 3.
    - **Gate 2, unstable set:** `make bench-unstable ENV=staging` (5 repeats), judged by the Keep/Undo rule (Rule 23). Observe-only changes may skip it and ride along with the next measured change.
    - **Gate 3, full suite before merging to `main`:** `make bench-full ENV=staging` (3 repeats; 11–29 minutes in 15 of 16 logged `telco-rebuild` full runs). It refuses unless the deployed code matches the current code (same source fingerprint) and one of these holds: there is no full run yet, the impact verdict is `FULL`, no source changed since the last full run, or `make smoke-impact` passed for this fingerprint. `make bench-full` rebuilds `history/eval_impact_map.json` after every full run, so the smoke requirement applies from the second full run on; the first full run on a fresh repo or CI runner is the bootstrap exception. The only override is `SKIP_SMOKE_GATE=1 REASON="..."`, logged to `history/impact_gate.log` (`SKIP_IMPACT=1` is an alias). After the run it writes `history/bench/full-<sha7>.json` and prints the Gate 3 verdict, which `make gate3` checks (without `REPORT=`, `make gate3` finds the full run for the current code the same way `make bench-holdout` does): **`strict 3/3 >= 90%` (`45/50`, requiring `p >= 96.55%`) AND `100%` majority (`>=2/3`, zero `0/3` or `1/3` evaluations)**, `0` tool errors, and a complete single-commit full run (every evaluation with all its scored tries; an incomplete run fails). Never write synthetic composite `full-*` records combining slices from different runs or git SHAs into `history/runs.jsonl`.
    - **Gate 4, hidden holdout:** `make bench-holdout ENV=staging` (`bench-holdout/` × 3 repeats), once. The holdout must run on the same code (same source fingerprint of `cxas_app/`, `lib/` and `evals/`) as a full visible run that passed Gate 3; a docs-only or history-only commit in between is fine (Rule 30).
23. **Keep or undo, by measurement, after a preflight check.** `make preflight` (`scripts/preflight.py`; alias `make auth-check`) runs automatically before every cloud target (`push`, `push-evals`, `setup-dlp`, `smoke-impact`, `bench-smoke`, `bench-unstable`, `bench-full`, `bench-holdout`); `SKIP_PREFLIGHT=1` skips it. It prints the Application Default Credentials (**ADC**) identity and quota project, warns if the quota project differs from the target project or `gcert` has expired, and fails with the list of missing permissions (`ces.apps.get`, `ces.apps.update`, `ces.apps.runEvaluation`, `ces.evaluations.create`). ADC refreshes its own access tokens; the real failure is the login itself expiring, which preflight catches (`telco-rebuild` lost about 13.2 hours across two expired-login gaps). For google.com projects, scripts must use ADC: plain `gcloud auth print-access-token` user tokens are rejected (`401 ACCESS_TOKEN_TYPE_UNSUPPORTED`). Compare each candidate run with the nearest-in-time baseline: `make bench-compare FROM=<before.json> TO=<after.json>` (`scripts/bench_summary.py`), reading `strict 3/3 | majority >=2/3 | individual`. **Keep a fix only when the targeted evaluations reach `3/3` and nothing else regresses** (and `avg_pass_turns` / `avg_pass_tool_calls` stay clean); otherwise **undo** (`git revert`) and record the attempt in `docs/experiment_log.md`.
24. **One mechanism per iteration (Two-Bucket Triage: Bucket A vs. Bucket B).** Group failing evaluations by shared root cause (the 7 Root-Cause Clusters and 3 Silent Escalation patterns in references/07), never by per-eval special cases. Partition fixes into **Bucket A** (zero-coupling additive leaf tool metadata and atomic sequential tool wrapping, which cannot alter existing control-flow branches and can be safely batched) vs. **Bucket B** (shared routing or eligibility thresholds, which must be isolated one at a time and smoke-tested against both the positive target and its negative twin; DESIGN_RULES rule 36). Fix in this order, preferring Python over prompt growth:
    - **Step A — Return the missing fact or follow-up FAQ field as a tool result field** (`lib/services.py`), scoped to the tool that owns the domain workflow (including pre-grounding two-step confirmation disclosures in lookup/auth tools, Turn N+1 follow-up FAQ fields in action/catalog tools, and localized status notes in data tools; DESIGN_RULES rules 5, 33, 35).
    - **Step B — Enforce it in code and wrap multi-turn chains atomically:** a state change, parameter format (`str | int | float` union types + `normalize_code`; DESIGN_RULES rules 22, 32), keypad (DTMF) parsing, payment decline state clearing (`card_last4 = ""` + `last_payment_method`), missing login (`NOT_LOGGED_IN` in money-moving tools), atomic single-turn wrapping of sequential tool chains, or empty-input support for info-first caller openers (DESIGN_RULES rule 34) makes the tool's `<tool>_impl` handle it deterministically. How replies sound (markdown, leaked identifiers, card-vs-phone last-4 preservation, and the fallback line for a text-less handover reply) is fixed in `lib/speech.py`, which the `speech_hygiene` `after_model_callback` runs on every reply (DESIGN_RULES rule 36).
    - **Step C — Only then change the prompt:** state both branches (`when true` and `when false`), refer to tool fields rather than training numbers or dates, forbid unreturned embellishments, never greet by profile `first_name`, and replace or merge existing `<step>` text instead of appending `CRITICAL:` bullets.
    - **Step D — Run `make ci` (`overfit-check` + `eval-contract`) → commit → `make impact` → `make push` → `make smoke-impact`:** 0 errors and 0 warnings (`NUMBER_IN_PROMPT`, `EVAL_VALUE_IN_FAKES`, `FAKE_DATA_IN_PROMPT`, `TEST_ID_IN_SOURCE`, `LEAKED_EVAL_LITERAL`, credential list size ≤ 8, `instruction.txt` ≤ 12,000 characters).

    Every entry in `docs/defects.md` and `docs/experiment_log.md`, and every fix commit, carries the **5-Part Engineering Rationale**: (1) prior failure diagnosis (conversation IDs, first wrong turn, tool inputs and outputs, every failing judge metric), (2) what changed, (3) why it works across inputs, not just the test, (4) exact `file:line` references, (5) alternatives considered and why they were rejected.
25. **One small change per branch, one fix mechanism per candidate.** Each fix attempt lives on a branch `fix/<n>-<slug>`, is ≤ 80 gross lines across ≤ 6 files, ships with a unit regression test that fails without the change, passes `make ci`, and is a single commit. Never bundle unrelated changes into one measurement, and never merge several fixes or optimizer winners into one candidate: when it regresses, you can't tell which part did it (DESIGN_RULES rule 30). Smoke every impacted evaluation, not only the ones you meant to fix.
26. **Task size = quota size.** Keep individual worker tasks ≤ 60 minutes of agent time, commit after every self-contained step so a quota freeze loses zero work, launch cloud evaluations as background tasks without polling loops, and commit before any cloud operation (`make push` refuses uncommitted changes in `cxas_app/`, `lib/` or `evals/`, and `make preflight` runs automatically).
27. **Parallel fixers, one cloud measurement at a time.** Fixer subagents may write code and run Gate 0 at the same time, each in its own git worktree (`../<agent>-wt/fix/<slug>`) on its own `fix/*` branch, never in the main checkout. Only the coordinator pushes to `-staging` and runs cloud evaluations, one branch at a time. `scripts/run_evals.py` aborts if another session overwrote the staging app mid-run (it compares `get_app().update_time` before and after).
28. **Commits read like a changelog.** Subject: `<area>: <what changed in plain English>`. Body: the 5-Part Engineering Rationale, defect ID (`DEF-nn`), PRD requirement (`REQ-n`), and before → after benchmark scores (`strict 3/3 | majority >=2/3 | individual`) with platform run IDs.
29. **State lives in two files plus one folder.** `docs/defects.md` (diagnoses by root-cause mechanism), `docs/experiment_log.md` (every iteration's rationale, alternatives, before → after `strict 3/3 | majority >=2/3 | individual` scores, keep/undo verdict), and `history/bench/` (one JSON summary per benchmark run, rendered into a static HyperText Markup Language (**HTML**) dashboard by `make dashboard`). After a context reset or quota freeze, read those three plus `git log -10` to resume without re-surveying the codebase.
30. **Hidden holdout evaluations are touched last, on the same code as a full visible run that passed Gate 3.** Holdout evaluations live in `bench-holdout/` and run only through `make bench-holdout ENV=staging` (Gate 4; DESIGN_RULES rules 19 and 28). The holdout must run on the same code (same source fingerprint of `cxas_app/`, `lib/` and `evals/`) as a full visible run that passed Gate 3; a docs-only or history-only commit in between is fine. `make bench-holdout` refuses unless the deployed code matches the current code and it finds that full run: `history/bench/full-<HEAD sha7>.json`, or else the newest `full-*.json` whose commit has the same source fingerprint as HEAD. It prints which full run it paired with and logs the pairing to `history/impact_gate.log`. That full run must pass Gate 3; otherwise `HOLDOUT_REASON="..."` is required (logged to `history/holdout_audit.log`). Re-running the holdout on a new commit also needs `HOLDOUT_REASON`, and `make bench-full BENCH_DIR=bench-holdout` is refused. **Report visible and holdout scores together only when both ran on the same code (same source fingerprint of `cxas_app/`, `lib/` and `evals/`).** Never inspect `bench-holdout/` during hill-climbing. Any holdout-driven fix needs the owner's approval and must be a generalizable, PRD-neutral rule; after it, run a full visible run (`make bench-full`) on that same code (same source fingerprint) before the holdout is reported or re-run.
31. **SCRAPI first; never reinvent the wheel.** Read SCRAPI's skills (`.agents/skills/cxas-*`, installed by the optional `uv run cxas init`) and `uv run cxas --help` **before** writing any new script. SCRAPI already covers building and linting (`cxas push`, `pull`, `lint`, `llm-lint`, `versions`; `make voice-audit`), testing tools, callbacks and sessions (`cxas test-tools`, `cxas test-callbacks`, `cxas run-session text`), and tracing and triage (`cxas trace …`, `make trace-replay`, `make trace-triage`, `cxas insights`, `cxas-loss-analysis`). Full list: [references/13-commands.md](.agents/skills/gecx-agent-playbook/references/13-commands.md).
32. **Optimizer output is a candidate, not a result.** Automatic optimizers such as ParetoLoop propose edits and score them. Score only complete N × 3 runs (never a run that timed out or stopped part-way), never cancel runs mid-flight, diff every optimizer edit for constraints it removed, and re-measure any candidate you keep with a full visible run and the holdout on one commit (DESIGN_RULES rule 29).
33. **Temperature stays `1.0`.** `0.2` made no measurable difference in `telco-rebuild` (`b5f6c72` at `0.2`: `41/50 | 48/50 | 138/150`; `14ad14c` at `1.0`: `40/50 | 47/50 | 137/150`), and the owner's decision is final (DESIGN_RULES rule 17). Don't use the global `gecx-3hr-sprint` skill.

## Commands
Everything runs through the Makefile. Select the target environment with `ENV=<name>`, which loads `environments/<name>.mk`. These are the commands a normal build uses:
```bash
make install                                  # install dependencies into .venv
make kickstart NAME=<agent> PRD=prd.md        # scaffold a router + specialist agent, six tools, lib/, tests/ and evals/ (TEMPERATURE ?= 1.0)
make ci                                       # Gate 0, offline: bundle-check, overfit-check, eval-contract, cxas lint (fails on warnings not in lint_waivers.json, and if cxas is missing), pytest + coverage, self-tests
make bundle                                   # copy the shared lib/*.py code into every tool and callback file
make overfit-check                            # scan prompts, lib/ and tool wrappers for test values, NUMBER_IN_PROMPT, EVAL_VALUE_IN_FAKES, and test IDs
make eval-contract                            # check lib/fakes.py against the visible tests in bench/dev/evaluations/ (same step as in make ci)
make voice-audit                              # voice readiness: app.json checks, plus the SCRAPI optimizer audit (rule A010 temperature == 1.0) when that skill is installed
make preflight                                # ADC identity, quota project and CES permissions; runs automatically before cloud targets (SKIP_PREFLIGHT=1 skips; alias: make auth-check)
make setup-dlp ENV=staging                    # create the Cloud DLP templates and set loggingSettings.redactionConfig (DRY_RUN=1 previews); then commit cxas_app/app.json and make push (DESIGN_RULES rule 26)
make impact                                   # list evaluation IDs impacted by changes since the last full run, plus a Verdict: line (BASE=<sha> to override)
make push ENV=staging                         # needs committed cxas_app/ lib/ evals/; pushes, creates version git-<sha7>, writes history/last_push.json
make push-evals ENV=staging                   # create or update the evals/ goldens, simulations and probes in the app
make smoke-impact ENV=staging                 # Gate 1: impacted evaluations x 3 on the pushed code (refuses unless the current source fingerprint is pushed)
make bench-smoke ENV=staging TARGETS=ID1,ID2  # Gate 1 (manual): the named evaluations x 3 repeats
make bench-unstable ENV=staging               # Gate 2: evals/unstable_set.txt x 5 repeats
make bench-full ENV=staging                   # Gate 3: every visible evaluation x 3; writes history/bench/full-<sha7>.json and rebuilds history/eval_impact_map.json (from the second full run on, needs a passing smoke-impact or a FULL verdict; override SKIP_SMOKE_GATE=1 REASON="...")
make gate3                                    # Gate 3 verdict: strict 3/3 >= 90%, 100% majority, 0 tool errors, complete single-commit full run (default: the full run for the current code; REPORT= to pick a file)
make bench-holdout ENV=staging                # Gate 4: bench-holdout/ x 3, only on the same code (source fingerprint) as a full run that passed Gate 3 (or HOLDOUT_REASON="...")
make bench-compare FROM=a.json TO=b.json      # keep-or-undo verdict for two benchmark reports (prints strict 3/3 | majority | individual)
make trace-triage CONV=<id>                   # sort one failed conversation into a failure category
make chat ENV=staging                         # talk to the staging agent in the terminal
make dashboard                                # build the static HTML hill-climb dashboard
make bootstrap                                # one-time CI/CD setup wizard (GCP service account, GitHub secrets)
```
`make help` lists every other target (for example `bench-record`, `bench-fetch`, `trace-replay`, `eval`, `gate`, `preview-up`, `pull`, `versions-compare`, `skill-assets`, `skill-assets-check`).

Raw `cxas` commands behind these targets and platform gotchas live in `.agents/skills/gecx-agent-playbook/references/13-commands.md`. Run `uv run cxas <command> --help` before using an unfamiliar flag. Remember: an overwriting `cxas push` resets app-level settings and deletes platform evaluation runs—always re-apply settings in the push step and run evaluations after pushing.

## Definition of Done
- `make ci` is 100% green: `bundle-check` clean, `overfit-check` 0 errors (`NUMBER_IN_PROMPT`, `EVAL_VALUE_IN_FAKES`, `FAKE_DATA_IN_PROMPT`, `TEST_ID_IN_SOURCE`, `LEAKED_EVAL_LITERAL`), `eval-contract` (`scripts/eval_contract.py`) green when `bench/dev/evaluations` exists, `cxas` installed and `cxas lint` at 0 errors and 0 warnings not listed (with a reason) in `lint_waivers.json`, `pytest` green with ≥80% coverage on every Python file and one test file per code file, suite self-tests `OK`, and `verify_mutations.py` catching 100% of injected tool/guard breakages.
- Prompt linters (`make llm-lint`, `make voice-audit`, and `cxas_prompt_linter.py` if available) have been run on every instruction, with all P0/P1 findings fixed or documented.
- **All 3 judge metrics green at the Gate 3 dual bar**: `bench-full` achieves **>=90% strict `3/3` (`45/50`) AND 100% majority (`>=2/3`, zero `0/3` or `1/3` evaluations)** across Custom Expectations, User Goal, and Hallucination with zero tool runtime errors, `make gate3` passes on that run, and `strict 3/3 | majority >=2/3 | individual` is recorded side-by-side in `docs/experiment_log.md` (with no synthetic composite `full-*` records in `history/runs.jsonl`).
- **Visible and holdout are measured on the same code.** The release holdout run (`make bench-holdout`) ran on the same code (same source fingerprint of `cxas_app/`, `lib/` and `evals/`) as the full visible run that passed Gate 3 (a docs-only or history-only commit in between is fine), and any visible + holdout total in docs or reports comes from the same code (same source fingerprint). Every holdout-driven fix had the owner's approval and was followed by a full visible run on that same code before the holdout was reported or re-run.
- `gate_thresholds.json` has `measured_on_model` and `judge_model` filled in with the exact models used.
- Cloud DLP is set up (`make setup-dlp`) and checked in a `make chat` session or the conversation logs (evaluations can't verify it).
- Audio simulation suite meets the task-outcome, SCRAPI speech naturalness (no language with median turn label `"Bot-like"`), noise-variant, and P50/P90 latency targets agreed in the TDD.
- The LLM judge agrees with human labels on ≥90% of `evals/calibration/`.
- CI gate is green on the exact model being shipped; live version is created; post-deploy smoke test passes.
- `docs/` and the HTML dashboard (`make dashboard`) match the code and `history/runs.jsonl` / `history/bench/`.
