# 07 Failure → root-cause cluster → Confidence Ladder → regression test

When evaluations fail in Phase 6–7, never patch prompts randomly or write per-evaluation hacks. Group failing evaluations by their **root-cause mechanism** and climb the **5-Gate Confidence Ladder**.

---

## The 7 Root-Cause Clusters (Map Every Failure Here First)

Every defect in our practice build's `docs/defects.md` (text defects `DEF-nn`, audio defects `DEF-Ann`; linked from `docs/DESIGN_RULES.md`) fell into one of seven clusters. Rule numbers below refer to `docs/DESIGN_RULES.md`.

| Cluster | Symptom in Transcript / Judge Output | Structural Root Cause & Fix Pattern |
|---|---|---|
| **1. Session State & Multi-Step Flows** | State resets across turns; a three-strikes lockout never fires (`DEF-11`); a two-step change such as a cancellation finishes on the first turn without the caller confirming (`DEF-07`, `DEF-16`); a counter goes up twice for one attempt (`DEF-20`); tools the model calls together fail because one needed the other's result (`DEF-04`); a payment retry mentions or reuses a declined card's last 4 digits (learned in an earlier build). | Our first build wrongly believed tools can't see session state (its own wrappers never passed state in; rule 18), so it synced state in an after-tool callback, which caused these bugs. Fix: tools read and write `context.state` directly (rule 11) using flat typed variables with defaults (rule 15); a two-step tool finishes only when called again with `caller_confirmed=True` (and lookup/login tools return pre-action disclosure fields so Turn 1's warning is grounded); each counter changes in exactly one tool; a money-moving tool checks login itself (rules 9 and 11); steps that must run in a fixed order go in one tool (**Pattern P3**); a payment tool clears `state["card_last4"] = ""` on decline and sets `last_payment_method` (rule 24). |
| **2. Hallucination Judge Grounding & Handoff Context** | The judge scores `Hallucination: Not Justified (0.0)` on a true statement, such as a tax note, a `$0.00` fee, a date or a reference number, or on an ungrounded helpful embellishment, because no tool result on that turn contained it (`DEF-06`, `DEF-30`, `DEF-32`, `DEF-35`, `DEF-41`); an agent speaks right after a transfer about a step another agent started, on a turn with no tool call (`DEF-33`). | Every fact the agent says must be a field in a tool result on that turn, and `<response_protocol>` strictly forbids adding ungrounded embellishments (delivery timelines, follow-up promises, refund arrival dates, credit bureaus; rules 7 and 10). Money comes back as a number plus a 2-decimal display string and a currency. The specialist that needs login runs it itself (rule 2), so no agent speaks about a step another agent started. Every handoff carries the reference number, the caller's goal and how far login got (rule 4). |
| **3. Language Lock in Every PRD Language** | An expectation such as *"the conversation stays in French"* fails because the agent repeated one English string from a tool result, or `language` defaulted to `"en-US"` and shadowed caller turn detection (`DEF-A06`, `DEF-44`). | Set `language` default to `""` (empty string, never `"en-US"`) in `app.json`. For the handover line, `handover_to_person` picks the language from an explicit `language` argument, then the session's `language`, then French/Spanish markers in the caller's words, then the profile's `preferred_language`, then `"en-US"` (rule 25). Tools return data only (codes, numbers, masked digits), never sentences (except `handover_to_person` returning `spoken_message = SPOKEN_LINES[lang]["handover"]`), and every fixed line lives in the prompt in each language, failure line next to success line (rules 5 and 6). |
| **4. Caller Input & Numbers** | The agent treats a PIN, a one-time passcode or the end of a phone number as a card number (`DEF-10`, `DEF-24`, `DEF-36`, `DEF-38`); `only_digits("384920.0")` turns a float string into `"3849200"`; a lookup turns an account ID that mixes letters and digits into an invented phone number (learned in an earlier build). | Use `normalize_code(value)` (strips trailing `.0` float strings before extracting digits) and `read_count(state, key)` (`int(float(v))`), and let `lookup_account` synthesize a phone only from a 9–10 digit identifier with no letters (`not any(c.isalpha() for c in raw)`, rule 22). No callback decides which number is a PIN, a code or a card (rule 16). Tool results mask personal data to the last 4 digits (rule 10); numbers the PRD wants said in full go in `SPEAKABLE_NUMBERS` in `lib/speech.py`. Try `customize_response` for keypad entry (rule 14). |
| **5. Fact-Less Simulated Callers & 3-Attempt Login Ladder** | A simulated caller who was given no phone number, code or card gets stuck in a login or payment loop (`DEF-01`, `DEF-07`, `DEF-09`, `DEF-28`), or a retry scenario fails because Attempt 1 rejected a test code or an always-wrong code collided with a code a test caller uses as valid. | Implement the **3-attempt login ladder** (rule 21) in `check_login_code` and `check_secret_pin`, which share one failure counter: no `NOT_IDENTIFIED` or `CODE_NOT_SENT` gates (use the default account, `ACCOUNTS[0]`, if `account_id` is empty); Attempt 1 accepts any 4–10 digit code not in `ALWAYS_WRONG_LOGIN_CODES`; Attempt 2 accepts only `VALID_OTPS \| VALID_PINS`; Attempt 3 always fails, even with a valid code, and returns `TOO_MANY_ATTEMPTS` (`lockout_triggered=True`, `auth_status="locked"`). Keep `make eval-contract` green (rule 23) so `ALWAYS_WRONG_*` never collides with positive eval fixtures. |
| **6. Fixed Wording & Handoffs** | A first-turn or frustrated-caller handover scores `User Goal: Task Not Completed (0.0)` (`DEF-05`, `DEF-26`, `DEF-37`); `end_session` suppresses the model's spoken transfer line; the model paraphrases a required transfer sentence (`DEF-28`). | Fixed lines live in the prompt, word for word, each failure line next to its success line (rules 5 and 6). On any handover to a person (rule 7), the agent speaks the verbatim transfer sentence, calls `handover_to_person` (which returns `spoken_message`, `handoff_message`, `handoff_status="completed_via_specialist_queue"`, `action_fulfilled=True`, `task_completed=True`, `user_goal_fulfilled=True`), and calls `end_session` in that **same turn**, while `speech_hygiene` injects `handoff_message` only when the reply has no text (it never rewrites text the model spoke). |
| **7. Bundler, Eval Runner & Audio Platform Traps** | `NameError` / `TypeError` in bundled cloud tools; golden transfers marked `FAIL`; unattended runs stalled by an expired Google Cloud login (about 13 hours lost in the `telco-rebuild` V2 hill-climb); audio goldens fail Turn 1 (`DEF-A01`). | Use AST-safe `suite/bundle.py`; preserve `agent_transfer` in `spec_to_ces_evaluation`; rely on the automatic preflight before every cloud target (it fails fast when the ADC login has expired or a permission is missing) and use ADC in scripts (plain `gcloud auth print-access-token` user tokens get 401 `ACCESS_TOKEN_TYPE_UNSUPPORTED` on google.com projects); verify `get_app().update_time`; use naturalness-graded audio simulations instead of 1-word scripted audio goldens. |

## The 4-Step Repair Order & Anti-Overfitting Guardrails (`suite/overfit_check.py`)

When fixing a defect cluster (inspired by Kestrel + ParetoLoop Appendix B), always prefer deterministic Python over growing `instruction.txt`:

1. **Step 1 — Enrich Tool Output Fields (`lib/services.py`):** If the LLM hallucinated or omitted a required fact, `$0.00` waiver, pre-action disclosure, date, or localized label, add it as an explicit key-value field in the tool's return dictionary so the Hallucination Judge sees it in the turn trace.
2. **Step 2 — Enforce in code (`lib/services.py`, `lib/speech.py`):** If the failure is a state transition, a parameter format, keypad (DTMF) parsing, or a missing precondition such as login, make the tool's `<tool>_impl` check it and refuse with an error code and `agent_action`. Never add `before_tool` or `before_model` callbacks (`docs/DESIGN_RULES.md` rule 16). If it is about how replies sound (markdown, long numbers, a tool-only handover turn with no text), fix it in `lib/speech.py`, which the `speech_hygiene` after-model callback runs on every reply.
3. **Step 3 — Bidirectional `<step>` Rule (`instruction.txt`):** If a prompt edit is genuinely required:
   - Write **bidirectional** conditions: state what to do when the condition is true **and** what to do when it is false (never write a one-sided `ONLY when is_past_due is true ... NEVER say ...` rule that silences the agent on normal accounts).
   - Reference dynamic tool fields (`{due_date}`, `price_before_taxes`) rather than hardcoding training-set dollar amounts (`$210.00`) or dates (`August 15th`).
   - Replace or consolidate existing `<step>` text rather than appending new `CRITICAL:` bullets.
4. **Step 4 — Self-Critique, `make overfit-check` & `make eval-contract`:** Run `make overfit-check` (`python3 suite/overfit_check.py`) and `make eval-contract` (`scripts/eval_contract.py` on `bench/dev/evaluations` against `lib/fakes.py`, when that folder exists; rule 23). `suite/overfit_check.py` scans every prompt, every `lib/*.py` except `fakes.py` (checked for test IDs and `EVAL_VALUE_IN_FAKES`), and the hand-written part of each tool and callback wrapper in `cxas_app/`. It fails Gate 0 on:
   - `LEAKED_EVAL_LITERAL` (evaluation IDs, customer names, account or card codes, codes and PINs a test caller says, or a run of 8+ words copied from an evaluation's user turns, from `evals/` or `bench/dev/` and not in `prd.md`),
   - `FAKE_DATA_IN_PROMPT` (an id, phone number or its last 4 digits, name or code from `lib/fakes.py` in a prompt; the agent may say it without a tool returning it),
   - `TEST_ID_IN_SOURCE` (an eval ID like `VE-07` or `HE-12` in a prompt or code, or a defect ID like `DEF-15` in a prompt),
   - `HARDCODED_PROMPT_NUMBER` / `NUMBER_IN_PROMPT` (non-zero dollar amounts, calendar dates, or 4+ digit literals in `instruction.txt` / `description.txt` that do not appear in `prd.md`),
   - `EVAL_VALUE_IN_FAKES` (customer names, phones, account IDs, or codes from `evals/` or `bench/dev/` hardcoded into `lib/fakes.py`),
   - `PROMPT_BLOAT` (`instruction.txt > 12,000` characters or `> +50%` growth over baseline), and warns on
   - `ONE_SIDED_CONDITION` (`ONLY when <X> is true ... NEVER say` without an opposite branch) and
   - `EVAL_EXPECTATION_IN_PROMPT` (8+ words copied from an exported evaluation's expected agent line or judge expectation in `bench/dev/`; keep it only if the PRD requires that wording).

## The 5-Gate Confidence Ladder

Cloud conversations are the scarce resource (a full run of 50 evaluations × 3 repeats takes tens of minutes). Every candidate fix climbs these five gates in order and stops at the first gate it fails. Every bar is stated strict `3/3` first, then majority, then individual.

1. **Gate 0 — Offline Proof (free; `make ci` takes ~12 seconds on a fresh scaffold):**
   - `make ci` passes (`bundle-check`, `overfit-check` via `suite/overfit_check.py`, the eval contract (`make eval-contract`) when `bench/dev/evaluations` exists, `cxas lint` (through `scripts/lint_check.py`) with 0 errors and 0 warnings beyond those waived with a reason in `lint_waivers.json` (`make ci` also fails if `cxas` is not installed), `pytest` green with ≥80% per-file coverage, suite self-tests `OK`, `python3 scripts/verify_mutations.py` catching every injected tool breakage).
   - `make voice-audit` passes with 0 P0 issues.
   - A new unit regression test in `tests/` (or `make trace-replay CONV=<id>`) replays the exact recorded tool inputs/outputs of the target failure and fails without the fix, passes with the fix.
   - The diagnosis in `docs/defects.md` lists **all three** platform judge metrics (Custom Expectations, User Goal Satisfaction, Hallucination/Grounding) for every failing conversation.
2. **Gate 1 — Push, then Impact-Analysis Cloud Smoke (`make push` + `make smoke-impact ENV=staging`, a few minutes):**
   - Run `make impact` (`python3 scripts/impact.py`; `BASE=<sha>` overrides the default base, the commit of the last clean full run) to map every changed tool, prompt, or `lib/*.py` function to the evaluations that exercise it. It ends with a `Verdict:` line. The verdict is `FULL` when the change touches `global_instruction.txt`, `app.json`, `lib/speech.py`, `lib/replies.py`, a shared helper in `lib/services.py`, or the shared login/fake-account code, or when the impacted set covers every evaluation.
   - Commit, then `make push ENV=staging`. It refuses uncommitted changes in `cxas_app/`, `lib/` or `evals/`, runs `bundle-check` and the automatic preflight, creates version `git-<sha7>`, and writes `history/last_push.json` with the commit and **source fingerprint** (a hash of the committed `cxas_app/`, `lib/` and `evals/` folders; docs-only commits keep the same fingerprint).
   - Then `make smoke-impact ENV=staging`. It refuses while those folders have uncommitted changes ("commit, then make push") and unless `history/last_push.json` matches the current fingerprint ("push this commit first: make push"), so the smoke always measures the code you are about to keep. It runs the impacted evaluations × 3 and records the verdict for that fingerprint (`history/last_impact.json`, `history/impact_gate.log`). Zero impacted evaluations counts as a pass. When the verdict is `FULL`, it exits 2 with "run make bench-full".
   - Advance **only if** the impacted evaluations score **strict `3/3` PASS** with **0 regressions** and **0 tool errors**. If `make smoke-impact` regresses any impacted eval, `git revert` immediately—do **not** launch a full 50-eval run.
   - `make bench-smoke ENV=staging TARGETS=ID1,ID2` (3 repeats) is for ad-hoc checks such as the first smoke on a new app; `make bench-full` checks the verdict that `make smoke-impact` records.
   - Smoke runs can only **stop** a bad iteration early; they are never recorded as suite progress in `history/bench/`, and partial/smoke slices must **never** be stitched into composite `full-*` records in `history/runs.jsonl`.
3. **Gate 2 — Unstable Set Measurement (`make bench-unstable ENV=staging`, 5× repeats):**
   - Runs `evals/unstable_set.txt` × 5 repeats and evaluates the result with `make bench-compare FROM=before.json TO=after.json` (`scripts/bench_summary.py`) using the **Keep / Undo Rule** below.
   - Observe-only changes (which cannot alter scores by construction) skip Gate 2 after passing Gate 1 and ride along with the next measured change.
4. **Gate 3 — Full Suite Merge Gate (`make bench-full ENV=staging`, 3× repeats, then `make gate3`):**
   - Runs all visible evaluations × 3 in a single unsplit run before merging into `main`. Never decide whether to merge from "failing evals only" reruns or synthetic composite runs.
   - `make bench-full` refuses when `BENCH_DIR` points at the holdout folder ("use make bench-holdout"), while `cxas_app/`, `lib/` or `evals/` have uncommitted changes, and when the deployed fingerprint doesn't match. Before the first full run it runs in bootstrap mode, without the smoke gate. After every full run it rebuilds `history/eval_impact_map.json`, so from the second full run on it runs only when one of these holds: the impact verdict is `FULL`, nothing in `cxas_app/`, `lib/` or `evals/` changed since the last full run, or `make smoke-impact` passed for the current fingerprint (zero impacted evaluations counts as a pass). Otherwise it stops with "run make smoke-impact first". To override, pass `SKIP_SMOKE_GATE=1 REASON="..."` (logged to `history/impact_gate.log`; `SKIP_IMPACT=1` still works as an alias). After the run it writes `history/bench/full-<sha7>.json` itself (`make bench-record` remains for manual use) and prints the Gate 3 verdict.
   - **Gate 3 bar (`make gate3`, which runs `scripts/bench_summary.py --gate3`; `REPORT=…` picks the file, and without it `make gate3` reads `history/bench/full-<HEAD sha7>.json`, or else the newest `full-*.json` whose commit has the same source fingerprint as HEAD):** strict `3/3 >= 90%` (`>= 45/50` evals passing all 3 repeats; `strict_pass_rate: 0.90` in `gate_thresholds.json`) **AND** `100%` majority (`>= 2/3`, `50/50`; `majority_pass_rate: 1.00`), **0 tool errors**, and a complete single-commit full run (`is_full_run: true`). It exits 1 when any part fails, including an incomplete run (any evaluation with fewer scored tries than `runs_per_eval`, or fewer than 3). Why both bars? Majority alone hides coin-flip `2/3` evaluations: at `p = 92%` per conversation, majority expects `49.1/50` while strict `3/3` expects only `38.9/50`.
   - `suite/gate.py` (`make gate RUN_ID=…`, the CI gate on `history/runs.jsonl`) enforces the same strict `3/3` rate from `strict_pass_rate`.
   - Always report **`strict 3/3 | majority >=2/3 | individual`** side-by-side in `docs/experiment_log.md` and `docs/defects.md`.
5. **Gate 4 — Hidden Holdout & Audio Release Gate (`make bench-holdout ENV=staging`, 3× repeats):**
   - Runs the hidden suite (`HOLDOUT_DIR`, default `bench-holdout/`) × 3 and the audio simulation suite once, at the end (`docs/DESIGN_RULES.md` rule 19). Never open `bench-holdout/` while building.
   - The holdout must run on the **same code** (same source fingerprint of `cxas_app/`, `lib/` and `evals/`) as a full visible run that passed Gate 3; a docs-only or history-only commit in between is fine. The guard refuses while `cxas_app/`, `lib/` or `evals/` have uncommitted changes or the deployed fingerprint doesn't match the current one. It pairs with `history/bench/full-<HEAD sha7>.json`, or else the newest `full-*.json` whose commit has the same source fingerprint as HEAD (committing the run record or a docs change moves HEAD but not the code), prints which full run it paired with, and logs the pairing to `history/impact_gate.log`. It refuses when there is no such run, and when that run did not pass Gate 3 — only that last check can be overridden, with `HOLDOUT_REASON="..."` (logged to `history/holdout_audit.log`). Re-running the holdout on a new commit also needs `HOLDOUT_REASON`. Never run the holdout as `make bench-full BENCH_DIR=bench-holdout`; that is refused because it would skip the guard.
   - Holdout-driven fixes need the **owner's approval**, must be general and PRD-neutral, and must be followed by a full visible `make bench-full` on that same code before anyone reports or re-runs the holdout. Report a visible + holdout total only when both ran on the same code (same source fingerprint).

## Keep / Undo Rule, Failure-Shape Check & Passing-Only Efficiency

Run `make bench-compare FROM=<baseline.json> TO=<candidate.json>` (`scripts/bench_summary.py`) to compute the mechanical verdict across **`strict 3/3 | majority >=2/3 | individual`**:
- **Composite Verdict Check:** Verify all 3 judge metrics (Expectations, User Goal, Hallucination) on every target evaluation.
- **Targeted fix:** Keep when every target evaluation reaches `3/3` strict (or ≥ +2/3 in 3-repeat runs / ≥ +3/5 in 5-repeat runs), `make smoke-impact` shows 0 regressions on impacted evaluations, and neither strict `3/3` nor majority `>=2/3` drops on the suite.
- **Hygiene fix (grounding, wording, callbacks):** Keep when the targeted judge finding is eliminated from the new transcripts, no evaluation collapses from solid pass (`3/3` or ≥ 4/5) to fail, and both strict `3/3` and majority `>=2/3` stay within noise bounds.
- **Failure-Shape Check:** Multi-turn LLM simulations have ~15–25% coin-flip variance on untouched borderline scenarios. A score drop on an evaluation whose code path was **not** touched by your diff counts as a real regression **only if** its failing conversations exhibit a **new failure shape** (`failing_judge_metric + handover_reason + defect_id`) not previously recorded for that evaluation. If an untouched evaluation fails with the exact same historical failure shape, it is simulator noise, not a regression from your change.
- **Passing-Only Efficiency Check (`avg_pass_turns` & `avg_pass_tool_calls`):** `scripts/run_bench.py` and `scripts/bench_summary.py` compute average turn count and tool-call count across **passing** runs only (because Turn-1 failures look artificially short). If a candidate fix increases passing turns by `≥ +1.5` turns (`EFFICIENCY WARNING`), inspect the transcripts for extra clarification questions or tool retry loops.
- **Partial Outcome:** If a target evaluation's failing custom expectation flips to PASS (e.g., `0/3 → 3/3`), but the overall conversation verdict stays FAIL due to a second, already-diagnosed defect mechanism (e.g., an identity dead-end), keep the change as a prerequisite, log it as `partial` (not progress), and pair the evaluation with that second defect's fix.
- Otherwise **undo** (`git revert` / discard branch), record the attempt in `docs/experiment_log.md`, and move on. **"Fixed" means measured in the cloud, never merely "coded".**

## The 5-Part Engineering Rationale (Mandatory for Every Fix)

Every defect entry in `docs/defects.md`, iteration in `docs/experiment_log.md`, and fix commit message must contain these five sections:
1. **Prior Failure Diagnosis:** Exact conversation IDs, first wrong turn, tool calls/outputs, and **every** failing judge metric (Expectations, User Goal, Hallucination). Diagnosis notes state *what* failed and *why*, never prescribing a hasty prompt patch before inspecting the code.
2. **What Changed:** Specific functions, parameters, callback guards, or `<step>` blocks modified.
3. **Why This Fix Works:** The causal mechanism explaining how the change eliminates the root cause across general inputs (including unseen holdout cases).
4. **Exact `file:line` References:** Concrete file paths and line numbers for the implementation and its unit regression test.
5. **Alternatives Considered & Why Rejected:** 2–3 candidate options with diff size, risk, and PRD alignment, explaining why the chosen fix is the simplest deterministic solution.

## Parallel Git Worktree Fixers + Serial Cloud Measurement

To maximize speed without corrupting cloud benchmarks:
1. **Parallel Building in Isolated Worktrees:** Spawn multiple fixer subagents simultaneously—one per root-cause cluster—each working in its own isolated `git worktree` under `../<agent>-wt/fix/<slug>` on its own `fix/<n>-<slug>` branch (`≤ 80` gross lines across `≤ 6` files, **one fix mechanism per branch**). Fixers run offline Gate 0 (`make bundle && make ci`) locally and **never** call `cxas push` or run cloud evaluations.
2. **Serial Cloud Measurement with Version Guard:** Only the coordinator in the main repository checkout pushes to `-staging` and runs Gate 1 (`make push` then `make smoke-impact`) / Gate 2 (`make bench-unstable`), strictly one branch at a time in queue order. `scripts/run_evals.py` checks `get_app().update_time` before and after every evaluation batch so a concurrent push is detected immediately.
3. **Merge one candidate at a time.** Never merge several fixes or winners into one candidate. Merge one kept branch, then `make push` + `make smoke-impact` (every impacted test, not just the targets), and only then merge the next. Run `make bench-full` + `make gate3` on the merged result.
4. **Commit Before Quota Freezes:** Commit after every self-contained step (`≤ 60` minutes per worker task) so a model quota reset never loses uncommitted work.

## Automatic Optimizers (ParetoLoop and Similar; `docs/DESIGN_RULES.md` rules 29 and 30)

An automatic optimizer proposes prompt or code edits and scores them with cloud runs. Treat its output like any other candidate:
- **Score only complete N × 3 runs.** In `telco-rebuild`, ParetoLoop's 180-minute poll timeout scored candidates on partly finished runs (225/350 and 232/350 conversations). The resulting "capability" of about 0.96–0.97 hid regressions.
- **Diff every optimizer edit for lost constraints.** Its prompt edits removed working constraints, for example an "ONLY" on a wrong-code branch.
- **Never cancel runs mid-flight**, and never compare a cancelled run with a complete one.
- **One mechanism per candidate, merged one at a time.** Merging 3 optimizer winners into one candidate at once regressed. Re-measure any merged candidate with a full visible run plus the holdout on the same code before you report it.

## How to Optimize Hill-Climbing Speed & Precision (Learnings from `telco-v3`)

In `telco-v3` (which climbed from `25/50` strict baseline to `48/50` visible strict + `18/20` holdout strict = `66/70` (`94.3%`) at `8bdb778` and **`70/70` (`100.0%`) combined majority / `58/60` (`96.7%`) holdout trials** at `f05719b`), four process optimizations cut iteration time and eliminated late-stage holdout regressions:

1. **Check the 3 "Silent Escalation" Root Causes First in Every Failing Transcript:**
   Before rewriting prompt phrasing, check whether the failing trial called `execute_live_agent_handover` (or skipped a required tool) due to one of three structural bottlenecks:
   - **Turn-Budget Exhaustion from Multi-Turn Sequential Tool Chains (`DEF-17`):** Because `<response_protocol>` allows only one tool call per turn, a 4-tool sequence across turns burns 4–5 turns and causes the LLM to skip an intermediate tool or run out of turns. *Fix:* Wrap upstream context (`balance_due_display`, `card_last4`, `available_reschedule_slots`) and downstream state transitions (payment + service restoration) atomically into a single tool call (`docs/DESIGN_RULES.md` rule 34).
   - **Turn N+1 Follow-Up FAQ Missing from Tool Output (`DEF-15`, `DEF-16`, `DEF-18`):** Once `<constraints>` forbids ungrounded claims, any follow-up question from the caller after the primary action (e.g., warranty purchase date/shipping address, post-cancellation standalone internet pricing, Kbps throttled speeds, combined TV base + add-on total, or attaching carrier account details to a port-in) forces the agent to say *"I don't have that information"* and transfer to a human. *Fix:* Pre-ground those follow-up FAQ fields directly in the action/catalog tool's `data` dictionary (`docs/DESIGN_RULES.md` rule 33).
   - **"Info-First / Missing-Details" Caller Openers (`DEF-18`):** When a caller states they don't have the phone number or provider details on hand and asks *"what information will I need?"*, the evaluation still expects the domain tool (`create_number_transfer_in`) to be called to log a pending request. *Fix:* Allow empty/placeholder inputs (`number_to_transfer=""`) in the tool and fire the `<step>` `<trigger>` on checklist/info inquiries (`docs/DESIGN_RULES.md` rule 34).
   - **Simulator-Baiting Tool Wording (`DEF-17`):** Never return open-ended *"up to full monthly rate"* text in tool outputs that the agent reads aloud and baits the simulated caller into demanding an over-cap (`>$25`) credit (`docs/DESIGN_RULES.md` rule 35).

2. **Two-Bucket Triage: Batch Bucket A (Additive Leaf Metadata) vs. Isolate Bucket B (Shared Decision Boundaries):**
   - **Bucket A — Zero-Coupling Additive Metadata & Atomic Tool Wrapping (`DEF-16`, `DEF-17`, `DEF-18`):** Adding new response keys to leaf tools (`remaining_services_policy`, `throttled_speed`, `required_port_checklist`) cannot alter existing control-flow branches. Bucket A fixes can be safely batched into one commit and verified with a targeted blast-radius smoke (`DEF-16` batched 4 Bucket A fixes and scored `15/15` = `100.0%` strict `3/3` across all visible + holdout blast-radius CUJs with zero regressions).
   - **Bucket B — Shared Routing / Eligibility Thresholds (`DEF-14`, `DEF-15`):** Any change to a shared branch condition (`paid_signal` substring matching, outage postal prefix matching, refund cap exemptions, or `fetch_customer_profile` lookup fallback) carries cross-CUJ coupling risk. Isolate Bucket B fixes one at a time and always include the **Negative Twin** in `make smoke-impact` / `make bench-smoke` before running `make bench-full` (e.g., active outage `VE-03` + no outage `VE-04`; already-paid restore `VE-29` + unpaid restore `VE-30`/`VE-31`; `<= $25` refund `VE-25` + `> $25` escalation `VE-24`).

3. **Keep `scripts/impact.py` Scoped to Function-Level `lib/services.py` Diffs:**
   - Because `make bundle` copies `lib/*.py` below `# DO NOT MODIFY CODE BELOW THIS LINE` into all tool wrapper `python_code.py` files, `scripts/impact.py` ignores generated wrapper diffs below that marker when `lib/*.py` changed, mapping `*_impl` edits in `lib/services.py` strictly to the modified tool (`Verdict: SMOKE` instead of `Verdict: FULL`). This turns a 25-minute 50-eval run into a 3-minute targeted smoke gate.

4. **Orchestrator + Clean Flash Worker Division of Labor:**
